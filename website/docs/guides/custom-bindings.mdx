# Custom bindings

Protocol binding implementations are distributed separately in `ByteBard.AsyncAPI.NET.Bindings`. For supported protocols, add the binding package and register its parsers with the reader. For example, `BindingsCollection.All` registers all built-in parser implementations; protocol-specific coverage is documented in the [bindings section](/docs/bindings).

To implement a binding that is not supplied, derive from the abstract generic binding class for its location: `ServerBinding<T>`, `ChannelBinding<T>`, `OperationBinding<T>`, or `MessageBinding<T>`. `T` is the concrete class itself and must implement the corresponding binding interface and have a parameterless constructor. A channel binding is sketched below:

```csharp
public sealed class FooBinding : ChannelBinding<FooBinding>
{
    public string Foo { get; set; }
    public string Bar { get; set; }

    public override string BindingKey => "foo";

    protected override FixedFieldMap<FooBinding> FixedFieldMap => new()
    {
        { "bindingVersion", (binding, node) => { binding.BindingVersion = node.GetScalarValue(); } },
        { "foo", (binding, node) => { binding.Foo = node.GetScalarValue(); } },
        { "bar", (binding, node) => { binding.Bar = node.GetScalarValue(); } },
    };

    public override void SerializeV2(IAsyncApiWriter writer) => SerializeV3(writer);

    public override void SerializeV3(IAsyncApiWriter writer) => SerializeProperties(writer);

    public override void SerializeProperties(IAsyncApiWriter writer)
    {
        writer.WriteStartObject();
        writer.WriteRequiredProperty("foo", Foo);
        writer.WriteRequiredProperty("bar", Bar);
        writer.WriteOptionalProperty(AsyncApiConstants.BindingVersion, BindingVersion);
        writer.WriteExtensions(Extensions);
        writer.WriteEndObject();
    }
}
```

Register the binding parser on the reader settings' `Bindings` collection to enable deserialization:

```csharp
var settings = new AsyncApiReaderSettings();
settings.Bindings.Add(new FooBinding());
var document = new AsyncApiStringReader(settings).Read(input, out var diagnostics);
```

## Binding keys in AsyncAPI 3

AsyncAPI 3 bindings objects only allow the binding names the specification lists (`amqp`, `http`, `kafka`, `ws` and so on) and `x-` extensions. The list follows the specification text, which also names `mqtt5` and `mercure` even though the AsyncAPI 3 JSON schemas leave them out. When a document is serialized as AsyncAPI 3, a binding whose `BindingKey` is not one of those names is written as an extension: `FooBinding` above appears as `x-foo`. The key in the object model stays `foo`, so `channel.Bindings["foo"]` and `TryGetValue<FooBinding>` work as before. `AsyncApiBindingKeys.ToV3Key` returns the name a key is written under. AsyncAPI 2 allows any key, so AsyncAPI 2 documents keep `foo`. A binding whose `BindingKey` already starts with `x-` is written and read under that key in both versions.

When reading an AsyncAPI 3 document, `x-foo` is read as the binding if a parser for `foo` is registered; otherwise it stays an extension. A registered custom binding under its bare key (`foo`) is still read, but the reader reports an error, since the document does not conform to the specification.

The binding's serialized fields must follow the relevant AsyncAPI binding specification. Custom bindings are separate from protocol-specific binding support already covered under [bindings](/docs/bindings); this page only documents the extension point. Confirm the exact parser type and signatures against the referenced package version when implementing a binding.
